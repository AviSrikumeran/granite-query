Why Granite 4.2 3B?

We chose Granite Language: ibm-granite/granite-4.2-3b as a small, open, already capable reasoning model for a controlled data-quality study. Its Apache 2.0 checkpoint is downloaded and verified, its size supports affordable adaptation, and keeping it fixed preserves continuity with our measured baseline.

Granite 4.2 already receives math, code and reasoning training. A coding model is also a language model with a different training emphasis; its math advantage has to be measured. We have not established that switching to Granite Code would improve this workload.

Teacher/reference: the general-purpose DeepSeek API model deepseek-v4-pro. Its larger scale supplies a reference for comparison; every proposed training answer still needs verification.

The capstone question

Better reasoning per unit of cost

Can verified, student-targeted training data improve a small general-purpose model's reasoning reliability per unit of training and inference cost, while preserving its other capabilities?

Math is the first testbed because we can inspect intermediate quantities and check numerical answers. The long-term contribution is a validation-and-selection method that can be tested on other workloads and students.

  1. Establish the data effect: compare targeted and random verified examples under the same training budget.
  2. Measure practical usefulness: report accuracy, all generated tokens, runtime, selection overhead and retention of tool, grounding and instruction behavior.
  3. Test transfer: repeat the method on a second workload, such as quantity tracking in grounded documents, and another student before claiming it scales.

Sparse upcycling remains a later conditional architecture experiment. The immediate research question concerns data selection for the existing dense checkpoint.

The next comparison changes which examples are selected. Both arms use the same verified pool, concise solution style, checkpoint, training settings and loss-token budget. An untouched Granite checkpoint remains the evaluation reference.

What would count as useful evidence?

Compare both trained checkpoints with the untouched base on the same frozen transfer questions in low-effort mode at a 2048-total-token cap. Report paired corrections and regressions, uncertainty, accuracy, total tokens, tokens per correct answer, truncation, runtime and the retention screen.

Keep training helps and targeted selection beats random selection as separate claims. Publish negative results too. A second training seed is a separately budgeted replication before a robust selection claim; practical improvement targets alone are not statistical proof.
