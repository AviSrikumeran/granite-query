# Interlocking blocks: violet material study

Live: https://avisrikumeran.github.io/granite-query/playground/purple/

Two synchronized views compare the accepted green material with a violet treatment on the same interlocking blocks. The homepage, accepted Modal-style study and green three-direction comparison are unchanged. All runtime files are isolated in this directory.

## Review controls

- **Purple material:** Blue violet uses indigo/blue shadows and violet/lavender highlights. Rose violet offers a warmer orchid variation. Both use ordered brightness tiers with pale highlights, rather than a single hue substitution.
- **Joints:** More separation narrows the beam sections and central bridges and moves the parallel modules farther apart. Both materials use exactly the same geometry. Reference spacing restores the accepted interlocking-block geometry.
- **Pose:** cycle or hold Locked, Open and Offset. Timing, selective flashes and center-out reveal follow the accepted renderer.
- **Link mouse views:** turn both views together, or inspect them separately. Arrow keys turn a focused view; Home resets it. Pause holds the formation clock while inspection remains available. Escape pauses.
- **Peripheral views:** off initially to make the joints easier to inspect; enable the surrounding fragments for the full field.

The new treatment includes its own background, peripheral tint, soft energy colors and bloom threshold. The green reference retains its material and lighting parameters. The lower-purple brightness threshold is intended to preserve glow without flattening the shaded faces.

The material comparison starts playing automatically. Reduced-motion preference starts fully revealed and paused. Hidden pages and offscreen views stop scheduling work. A simpler Canvas fallback is retained.

Review URLs: ?at=4 freezes a settled comparison; &spacing=reference restores the accepted geometry; &material=orchid selects Rose violet; &ghosts=1 enables peripheral views; &intro samples the reveal; ?renderer=canvas&at=4 inspects the fallback.

## Accepted direction and next animation

The user prefers interlocking blocks and proof branches. Nested frames remain in the earlier comparison for reference and are not the next direction to pursue. The blocks suggest a distinct material; the branches suggest connections and a path through evidence.

The proposed original sequence combines both directions around **query → select → extract → expand → connect**. It is a future motion prototype, separate from this material release.

| Beat | Proposed visual |
| --- | --- |
| Query | A new Granite Query modular cube mark sits in an organized, closed configuration. A selected region lights up. |
| Select | The proof-branch structure becomes an abstract three-pronged gripper. It descends and closes around the highlighted block. |
| Extract | One housing section moves aside. The gripper lifts the violet core out while a neighboring section settles onto its side. |
| Expand | The extracted block stretches into separated modules, exposing a luminous inner structure. |
| Connect | Modules settle into a branching network. Scrolling reveals connected evidence or reasoning steps. |

Build the mark as editable geometry with an SVG export for static use. Name the housing, selected core, gripper and nodes as separate groups. A parameterized timeline can drive their translation, opening, light and connection growth; normalized scroll progress can scrub the sequence. Keep a completed, still composition for reduced motion. No prerecorded animation, generated video or credit-based service is needed for this architecture.

The first prototype should settle the mark's silhouette, gripper contact poses and the core's expansion before adding secondary effects. Lighting should make the selected piece and its contact points readable at each beat. The logo can be designed as an original Granite Query mark using the modular language established here.

## Research information that formats itself

The current repository already has structured publication feeds:

| Existing source | Proposed presentation responsibility |
| --- | --- |
| docs/status.json and docs/events.json | Current stage, next action, timestamps and event journal. |
| docs/project-status.json | Project summary, model, completed work, current work and remaining work. |
| docs/research.json | Experiment comparisons and figure references. |
| docs/paired-results.json and the dedicated result feeds | Evaluation context, method comparisons and reported metrics. |

granite_query/cloud/progress.py already publishes sanitized status/events snapshots, and docs/index.html currently refreshes the status feed every sixty seconds. The next site can reuse those feeds through one normalization layer and reusable presentation components. No publication pipeline is changed by this study.

Proposed information order: a clear research question and project identity; current experiment status; comparable result summaries; methods and evidence detail; a dated journal. A result record should determine its model/dataset labels, evaluation context, metric formatting, status and evidence links through a stable template. New records then populate the existing layout automatically. The animation provides the visual narrative, and the content structure gives visitors a clear route into the research.

## Verification and publishing
