We chose Granite Language: ibm-granite/granite-4.2-3b as a small, open, already capable reasoning model for a controlled data-quality study. The capstone question

Better reasoning per unit of cost

Can verified, student-targeted training data improve a small general-purpose model's reasoning reliability per unit of training and inference cost, while preserving its other capabilities?

Math is the first testbed because we can inspect intermediate quantities and check numerical answers. The long-term contribution is a validation-and-selection method that can be tested on other workloads and students.

  1. Establish the data effect: compare targeted and random verified examples under the same training budget.
  2. Measure practical usefulness: report accuracy, all generated tokens, runtime, selection overhead and retention of tool, grounding and instruction behavior.
  3. Test transfer: repeat the method on a second workload, such as quantity tracking in grounded documents, and another student before claiming it scales.

Sparse upcycling remains a later conditional architecture experiment. The immediate research question concerns data selection for the existing dense checkpoint.

Decision and research goal

Keep ibm-granite/granite-4.2-3b, revision 4e9c275e232f10211ec88644d106a1f6a1b60e06, as the fixed student. It is an already post-trained, general-purpose reasoning model with math and code training. We have not established that it is the best model overall or that a Granite Code checkpoint would score higher on our math workload. A coding checkpoint is another language model with a different training emphasis; there is no separate coding department to remove. IBM model card, Granite Code documentation.

The API teacher/reference remains deepseek-v4-pro, a much larger general-purpose model. Its answers require verification, as the paired error review demonstrated. Its score is a teacher comparison, not a parameter-matched architecture test. DeepSeek model documentation.

Long-term goal: improve a small general-purpose model's reasoning reliability per unit of training and inference cost through verified, student-targeted data, while preserving its other capabilities.

Math is the initial testbed because intermediate quantities and numerical answers can often be checked. The scalable contribution is the validation-and-selection method. Later transfer studies should test another workload, such as quantity tracking in grounded documents, and another student. Math gains alone do not establish broad assistant improvement. What has already been learned

The 32-question mode study retained 448 outcomes. Granite low effort matched 27/32 references with 6,858 generated tokens at either tested cap. All three clear low-effort process failures were solved by both DeepSeek nonthinking and Granite nonthinking in the preserved samples. The leading hypotheses concern unit preservation, complete quantity ledgers and consistent entity dependencies. Mode and decoding differ, so these observations do not prove a deterministic mode effect.

There are 15 checked candidate seed examples: nine existing TRAIN questions and six authored contrasts. They contain 905 raw target tokens before native serialization and EOS. They are a review specification, not an adequate frozen training pool or evidence that training helps. Two reference-sensitive development questions stay excluded from corrective supervision. Evaluation and decision

Evaluate all three checkpoints on the same frozen 100 transfer-development questions. The primary setting is native low effort, cap 2048 for reasoning plus final output, temperature 1.0, top-p 0.95 and common per-question decoding seeds derived from seed 17. Use the same warm device, engine, precision and batch settings. Granite inference settings.

Report reference-match accuracy after reference QA, paired corrections/regressions, paired question-bootstrap 95% intervals, all generated tokens, tokens per correct answer, truncations, failures and runtime. Also report data verification/selection overhead, forwarded training tokens, GPU time and dollars. Keep the existing 200-question cohort diagnostic. Include secondary low-effort-512 and nonthinking-2048 checks only when covered by the bounded evaluation plan, and label them separately.

Keep two claims separate: training helps versus untouched base, and targeted selection helps versus random verified data. A practical pilot screen is at least three percentage points of accuracy improvement at comparable measured inference cost, or at least 20% fewer generated tokens per correct answer with at most one percentage point accuracy loss, compared with both reference conditions, while passing retention checks. These are proposed engineering screens, not statistical proof.

Publish every pilot outcome. Question-bootstrap intervals do not cover training-seed uncertainty. A separately budgeted repeat of the full paired comparison with training seed 43 is required before claiming a robust selection advantage. If no advantage appears, retain the best-supported base/prompt configuration and document the null or negative result. Keep the existing official-test protocol sealed until the final candidate and inference rules are frozen.

    Granite weights and efficiency research plan
    

    Priority: High. Reviewed November 3, 2026. Status: artifact audit and a separate 32-question inference diagnostic complete; training interventions and sparse conversion remain proposals.
    

    Granite Query should measure whether verified, student-aware training data improves useful mathematical work per unit of training and inference cost. A universal claim that Granite is ten times less efficient is not established. The immediate research question is narrower: Where does this exact Granite checkpoint spend resources without producing correct answers, and which affordable intervention changes that tradeoff?
    

    Which Granite we have
    

    The selected family is Granite Language. The training student is the post-trained text-generation and reasoning model ibm-granite/granite-4.2-3b, revision 4e9c275e232f10211ec88644d106a1f6a1b60e06. This is the language checkpoint used for the math project, not a dedicated code, forecasting or geospatial checkpoint. The earlier local Ollama demonstration used the larger language model granite4.2:8b in Q4_K_M format. Those artifacts are different sizes and precisions; do not join their results into one baseline.
    

    The pinned 3B checkpoint is now downloaded locally: two BF16 Safetensors shards totaling 7,319,517,120 bytes, each verified against Hugging Face's LFS SHA-256. Header inspection counts 3,659,737,600 stored parameters, 40 transformer blocks, width 2560, MLP width 8192 and vocabulary 100352. The complete local scalar audit and download receipts are included in the downloadable evidence. No new model inference or training was required for this audit.
    

    The selected family also offers 8B and 30B releases. Their inspected inventories contain about 8.79B and 29.28B elements, respectively. The 30B reference requires about 58.55 GB for its BF16 weight files alone. It is a larger capability reference, not a proven best choice for every workload. Keep the 3B student to preserve continuity and affordability. Official family.

    What Granite does and what weights mean
    

    Granite predicts the next token from the preceding context. Post-training makes that mechanism useful for answering questions, following instructions, reasoning and emitting tool requests. A host program must execute tools. Granite 4.2 supports thinking, non-thinking and low-effort modes; its official card recommends temperature 1.0 and top-p 0.95. Our historical greedy non-thinking 512-token protocol is a specific operating point. IBM model card.
    

    Weights are learned numerical arrays. The architecture specifies how to use them; the tokenizer maps text to token IDs; the chat template marks roles and reasoning modes. The weight files are neither a readable rule book nor a reconstruction of the training corpus. Different models learn different coordinate systems, so comparing the same array position across independently trained models cannot identify the same concept.
    

    For this Granite checkpoint, model.layers.0.self_attn.q_proj.weight has shape [2560, 2560]; k_proj and v_proj each have shape [512, 2560]. The MLP contains two [8192, 2560] projections and one [2560, 8192] projection. These are concrete inspection targets. Scalar samples and heatmaps show actual values, but their magnitudes and colors do not rank intelligence or establish a cause of inefficiency.
    

    Granite 4.2 is dense, whereas some 4.0 releases are hybrid Mamba and MoE models. The family name alone does not specify architecture. IBM documents pretraining inherited from Granite 4.1, supervised fine-tuning and staged reinforcement learning; the 8B and 30B variants additionally receive agentic RL. IBM technical walkthrough, 4.0 architecture.

    What the local tokenizer diagnostic found
    

    Fifteen newly authored strings cover math, prose, code, structured text, French, Chinese and Arabic. They contain no benchmark questions. Six English math strings encode to 162 Granite tokens, 179 Ministral tokens, 177 Falcon tokens, 162 Olmo tokens, 175 Qwen3 tokens, 175 R1-Distill-Qwen tokens, and 162 tokens under each inspected DeepSeek V3/V4 tokenizer. Granite therefore used about 7.4% fewer input tokens than Qwen3 on this small subset.
    

    This is a reproducible probe, not a representative benchmark or inference result. It excludes role templates, generated reasoning, answer correctness and execution speed. It argues against treating an assumed tenfold input-token penalty as the starting fact.
    

    The single Chinese diagnostic string goes the other way: Granite uses 40 tokens, Qwen3 uses 25, and DeepSeek V3/V4 use 22. That is a reason to stratify tokenization by workload and language, not to generalize from the English subset.

Granite truncations fell from eight to two after either adapter, while correctness fell. Shorter or more complete outputs alone are insufficient. These are development observations, not final-test scores. Project evidence, human study.

    What IBM's training documentation establishes
    

    Granite 4.2 LLMs: How They're Built is the primary training-method reference for this checkpoint. It describes supervised instruction/reasoning training, data filtering and deduplication, then staged reinforcement learning. This makes data validation a concrete intervention to test; disclosure of a recipe does not provide every training example or establish a causal explanation for our observed errors.
    

    Its underlying pretraining recipe is documented separately in Granite 4.1: How They're Built. Phase 1 is approximately 59% CommonCrawl, 20% code, 7% math, 10.5% technical, 2% multilingual and 1.5% domain-specific content. Later phases change the mixture, including more math, code and reasoning. These are phase-specific proportions, not percentages for the entire final checkpoint. Neither article establishes that patents dominate this model's training data. Structured conversations and output schemas also differ from training chiefly on structured business records.
    

    Research implication: IBM already performs data-quality checks, so adding a validator alone is not evidence of a novel improvement. Classify failures by correctness, units, scope, formatting and excessive generation; validate candidate training examples against those categories; compare selection against matched random controls. Preserve instruction following, tool validity and grounding while measuring any math improvement. Do not infer a training-data cause from tensor values or a verbose answer alone.
    

    Enterprise behavior to preserve
    

    IBM chooses the architecture, training data and optimization objectives; training learns the individual weight values. The enterprise positioning is a set of priorities to test. IBM documents additional agentic RL for the 8B and 30B variants, while our 3B student follows the shorter foundational and alignment path. Its final alignment stage includes a reasoning-length penalty. Excessive output should therefore be investigated as an observed behavior, rather than assumed to be an intentional integration requirement. IBM technical details.
    

    Integration combines learned behavior with software interfaces. Valid tool names and arguments are model behaviors; serving protocols, authentication and connectors belong to the surrounding application. A standard API does not establish universal workflow compatibility. The model and its deployment stack need separate tests.

    Sparse upcycling proposal
    

    Sparse upcycling copies selected dense feed-forward blocks into multiple experts and adds a router selecting a subset per token. It reuses the pretrained checkpoint and adds capacity. It is different from pruning weights, quantization and LoRA. The original paper evaluates T5 and vision models, including substantial continued training; its savings relative to starting over are not a guarantee of a cheap Granite run. Sparse Upcycling.
    

    An illustrative first topology replaces eight of forty Granite MLP blocks with four cloned experts, routing top one. Each MLP has 3 × 2560 × 8192 = 62,914,560 parameters. Three extra copies across eight layers add 1,509,949,440 parameters; bias-free routers add 81,920. Total capacity becomes 5,169,768,960 parameters, approximately 10.34 GB of BF16 weights before caches, activations, gradients or optimizer state. Top-one routing keeps the selected MLP arithmetic near the dense baseline while adding routing and dispatch overhead. It promises neither fewer tokens nor faster inference.
    

    Before training, use identical clones, dropout disabled, no dropped tokens, and a selected-expert output normalized to coefficient one. Verify logits against the original model on synthetic inputs within numerical tolerance; save/reload and verify tensor identity. Merely multiplying a copied expert by its unnormalized router probability can break preservation. Then test routing balance, expert usage, overflow, specialization and basic instruction retention. A later partial reinitialization ablation can test diversification only after the cloned baseline is sound. Drop-Upcycling.
    

    The router's training rule needs its own design: renormalized hard top-one routing can remove the main-loss gradient to gate scores. Before a paid experiment, demonstrate a differentiable or straight-through routing recipe, its balance objective and nonzero intended gradients on synthetic cases. Initial function preservation is a conversion check, not a complete learning algorithm. Cloning alone adds no new knowledge.
    

    The local GPU is an RTX 3060 with 12 GB VRAM. Raw weights fitting does not imply full training fits. Estimate activation/optimizer memory and supported sparse kernels before any funded run. The existing $30 Modal and $20 DeepSeek ceilings are shared with ongoing project work; do not budget them a second time.
    

    Staged plan and decision gates
    

      

    1. Freeze artifact evidence. Retain revisions, hashes, canonical tensor inventories, tokenizer probes and scalar samples. Keep raw checkpoints private and outside Git. This audit completes that step for the downloaded Granite student and the stated comparison scope.
      2. 

    2. Locate the bottleneck. Expand tokenization diagnostics on training/development text only. Plan native-mode cost curves and a paired error taxonomy. Keep the official test sealed and preserve existing studies as separate protocols.
      3. 

    3. Try the least expensive intervention first. Resolve template/masking defects if present. Compare complete concise and reasoning supervision with unchanged data controls. Existing independently versioned training work must retain its own ownership, reservation and reporting.
      4. 

    4. Evaluate the original data-valuation hypothesis. Compare selected and random subsets at equal supervised tokens and updates. Report accuracy change, uncertainty, input exposure and selection overhead. A useful checkpoint and evidence that ranking helps are separate claims.
      5. 

    5. Gate sparse conversion on evidence and resources. Require a working conversion/reload test and a funded memory/runtime estimate. Compare continued dense training with upcycled training under a shared data recipe. Use both an equal-token comparison and a separate equal-GPU-budget comparison; MoE overhead can prevent matching both at once.
      6. 

    6. Freeze and evaluate. Select the candidate using development data, freeze hashes and inference settings, then use the reserved official-test protocol once. Publish paired corrections/regressions, accuracy-cost curves, failures and reproducible commands. No gain is guaranteed.
      7. 

    

    An initial proposed usefulness target is at least three percentage points of development improvement at similar measured inference cost, or at least 20% lower measured inference cost with no more than one percentage point of accuracy loss. These are planning targets, not achieved results or statistical proof. Require paired uncertainty and additional seeds before stronger claims; use final evaluation for the frozen conclusion.
    

    The capstone contribution can be a reliable account of which verified examples improve a fixed student under a budget, backed by controlled evidence. Matching a frontier teacher or rebuilding a foundation model is unnecessary. A negative selector or upcycling result remains informative if the protocol isolates the cause and the evidence is reproducible.
    

    Reproduce the artifact audit
    

    Use the existing project Python environment with requests, numpy and tokenizers installed. From the repository root:
    

    python research/inspect_models.py metadata
python research/inspect_models.py download
python research/analyze_artifacts.py
python research/sample_weights.py

    

    The metadata command resolves comparison main revisions at execution time; this report's exact observed revisions remain in research/model_inventory.json and the public evidence bundle. Repeating the comparison later may inspect a newer release state. Granite's download is fixed to the existing project revision. These scripts make public HF requests and perform file inspection only; they do not train or execute remote model code.
    

    To reuse the exact comparison revisions from this audit, run python research/inspect_models.py metadata --manifest research/model_inventory.json instead of the unpinned metadata command. The page builder additionally uses markdown-it-py: python research/build_research_page.py regenerates the HTML after all audit outputs exist.
