## One bounded pass

1. Choose one unresolved question from the queue. Write the visual outcome and protected files before implementation. Reuse captured references first; inspect at most two new sources when the existing evidence cannot answer it.
2. Inspect the exact component and relevant motion. Record source URL, capture date, observable behavior, construction evidence and remaining inference. A repository is implementation evidence only when its source matches the component. Check asset licenses before reusing assets. Do not infer conversion performance from an attractive screenshot or social reaction.
3. Build one candidate against the preserved baseline in an isolated playground folder. Keep editable code, motion parameters and meaningful controls. Do not add a framework, service or paid tool without a concrete need.
4. Review the rendered specimen against the stated outcome. Allow up to two focused correction passes. If the remaining mismatch cannot be resolved within that scope, record it and deliver the useful comparison rather than repeat open-ended polishing.
5. Save a review containing a live URL, baseline/candidate screenshots at matching viewport and pose, relevant motion samples, what changed, verification and unresolved differences. Recommend Keep, Adapt or Pass with concrete reasons. Visual judgment remains a judgment, not a measured usability result.
6. Publish authorized playground work with a focused GitHub diff. Add each new experiment to the index and link back from it. Record the owner's verdict in the decision table before the next pass.

Two sources and two correction passes are workload limits, not guaranteed credit or dollar caps. Record actual usage only when a tool or usage report provides it. Do not invent token totals or equate training spend with design-chat usage. Avoid rereading the full repository, repeated unchanged captures, unnecessary dependencies and duplicate research.

## Review before delivery

| Check | Evidence to collect |
| --- | --- |
| Shape and material | Compare the same pose at the same scale; verify silhouette, readable negative space, distinct planes and concentrated highlights. |
| Motion and input | Inspect startup and transition; try pointer movement at both ends, pause/replay and keyboard input where applicable. Preserve reduced-motion and hidden/offscreen behavior. |
| Layout and usability | Inspect desktop and narrow-screen layouts, visible keyboard focus, control labels and navigation. Essential content must survive without animation. |
| Research communication | A reader can identify the question, current stage and evidence route without opening a paper. Show outcome, comparison, dataset/count and caveat before optional method detail. |
| Truth and completeness | Derive claims from the published feeds. Show pending, failed, stale and unavailable states. A simulated explanation must not appear to be live training. Negative and inconclusive findings remain visible. |
| Release scope | Check relevant syntax and behavior, direct links and console errors. Preserve unrelated remote blobs, especially homepage and research outputs. Report missing checks plainly. |

Complete relevant checks once. Broaden or repeat them only after a change, failure or unresolved concern. Do not add tests that merely restate an HTML link or CSS declaration.
